# 为BTF添加内联函数调试信息以支持内核追踪

BPF 程序依赖 BTF（BPF Type Format）调试信息来确定如何与内核函数交互。追踪内核函数需要在内核的 BTF 段中找到其地址——但对于已被内联的函数，没有单一、特定的地址，这一机制无法工作。Alan Maguire 在 2026 年 Linux 存储、文件系统、内存管理与 BPF 峰会（LSFMM+BPF）上主持了一场关于向 BTF 添加内联函数信息的会议。

## 问题背景

- 内核中有超过 100,000 个内联函数，分布在五倍多的调用位置。
- 部分函数是**部分内联**的：在某些位置正常调用，在其他位置被内联。
- 这导致当前可能出现“追踪成功”的假象，但实际部分调用未被捕获。
- 好消息是，支持内联函数追踪的其余基础设施（kprobes 可附加到任意位置）已经就绪。Maguire 表示：“故事其实已经相当完整了。”问题仅在于如何将函数内联位置的数据变成可用格式。

## 方案设计

DWARF 调试格式已有内联信息表示方式，但难以处理，且无法简单表示常见情况。BTF 方案应当：

- 紧凑；
- 支持去重以降低内存开销；
- 理想情况下，内联信息存放在内核二进制的独立段中，或作为独立内核模块分发，按需加载。

### 三项新增信息

Maguire 提议向 BTF 增加三种信息：

1. **location section（调用点专属信息）**：记录每个调用点内联了哪个函数，以及在未内联情况下应如何调用。由于该数据与具体调用点绑定、难以去重，因此应尽量由指向可去重数据的指针组成。
2. **location prototype（调用点原型）**：指定内联函数参数在调用点的表示方式，即指向 location parameter 条目的指针列表。
3. **location parameter（调用点参数）**：每条记录如何访问单个函数参数。

### 去重效果

理论上，编译器可对每个内联调用点（共 538,090 个）将函数参数存储在不同位置；实践中，编译器转换参数的方式有限，且许多函数签名兼容导致编译器做出相同选择。当前内核中，对 location prototype 去重后仅剩 **57,141** 个不同条目，引用总共 **17,535** 个 location parameter 条目。location section 因此占据大部分新增数据。

### 体积估算

BTF 新增数据总量约 **11MB**，即每个内联调用点约 21 字节。若拆出为独立内核模块并压缩，总量降至 **3.5MB**。

## 示例

考虑函数：

```c
int foo(int a, void *b, bool c);
```

若编译器内联 `foo()` 时消除了未使用的 `a`、将 `b` 提升为寄存器传递、并确定 `c` 为常量，BTF 表示为：

- 单个 location section 条目：存储 `foo()` 的 BTF 类型 ID、调用点相对内核基地址的偏移、指向 location-prototype 条目的指针。
- location-prototype 条目：带长度标签的 location-parameter 引用数组：
  - 第一项为 null，表示 `a` 无法恢复；
  - 第二项指向带标志的 location parameter 条目，标志值在寄存器中，并记录 `b` 的具体寄存器号；
  - 最后一项带不同标志，表示常量，并记录 `c` 的常数值。
