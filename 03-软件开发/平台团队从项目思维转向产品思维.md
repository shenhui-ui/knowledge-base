# 少开会、讲契约：平台团队如何降低跨团队协作成本？

## 核心观点

平台团队不能只关注项目交付，而应从**项目思维转向产品思维**。Eugenia Bergman 和 Hagen Tonnies 在 KubeCon & CloudNativeCon Europe 上分享了平台工程实践中的关键转变：

- 引入**生产者-消费者模型**，简化团队间交互关系。
- 用**接口和契约**替代会议和中间人的协调方式。
- 平台能力的“完成”定义：被目标消费者真正使用才算完成。

## 关键实践

### 生产者-消费者模型

- 提供能力的团队是**生产者**，使用能力的团队是**消费者**。
- 生产者定义清晰的接口和预期；消费者通过这些接口交互，避免临时协调。
- 一条实用法则：**如果两个团队需要定期开会协调工作，那么它们之间的接口很可能没有明确定义。**

### 产品导向的“完成”定义

最初“完成”意味着按范围和时间表交付，但对平台不适用。产品导向的完成标准是：

> 一项能力只有在集成到平台生态系统中、拥有文档且易于理解、获得支持且可以运维，并且真正被目标消费者使用时，才算完成。

评估进展时问：**“它有人使用吗？”** 和 **“它是否减少了用户的阻力？”**

### 契约驱动的协作

- 每个产品领域由产品负责人和首席工程师代表，共同与其他团队对应人员沟通。
- 定期沟通（通常融入冲刺节奏）讨论并完善“提供内容与预期回报”之间的契约。
- 明确生产者 API 的承诺与消费方的义务，基于真实用例（80% 路径）持续交付价值。

### 追踪平台使用情况

结合运维信号和产品导向信号：

- API 请求量
- 活跃消费者数量
- 配置活动
- 特定能力随时间的使用情况

不同能力的时间周期不同，但核心是**交付功能不等于交付价值**。

## 领导层的促成力量

- 领导层支持不是自上而下的命令，而是为转型创造共识、信任和演进空间。
- 支持实验、接受迭代，承认从项目转向产品会改变团队规划、优先级和成功衡量方式。
- 建立**组织层面的错误预算**，让团队探索新方法、从失误中学习，而不必承受僵化预期的压力。

> 这种安全感让我们能够将转型视为一个学习系统，进展来自理解预期与结果之间的差距，并根据这一信号持续改进。

## 启示

平台工程的核心不是交付功能，而是让能力被真正采用。通过清晰的所有权、显式的契约和基于使用数据的反馈，可以减少跨团队协调成本，逐步建立以产品为导向的平台模式。
