# How Compaction Works in Pi

> 原文来自 Earendil Engineering，讲解编码代理（如 Pi、Claude Code、Codex）中的上下文压缩（compaction）机制。

## 问题：LLM 上下文窗口限制

LLM 有有限的上下文窗口，这是模型在生成响应时能“看到”的输入范围。编码代理的每次请求包含系统提示、加载的文件（如 AGENTS.md）、工具定义以及对话历史。随着工作持续，对话历史不断增长，一旦超出上下文窗口，LLM 将拒绝请求，报错如 `Request exceeds the maximum size`。

## 处理上下文溢出的两种方案

1. **开启全新对话**：丢弃所有累积上下文，但会丢失之前的决策和未完成的工作。
2. **创建更小的上下文表示**：即压缩（compaction），保留对话的精华并继续当前会话。

## 压缩的实现

压缩通常使用 LLM 请求来总结对话历史，用一个压缩表示替换部分旧内容，为新消息和工具调用腾出空间。

## Pi 的具体实现

- 压缩在对话过长时自动触发，也可通过 `/compact` 命令手动触发。
- 自动压缩在每个回合结束后检查；如果遇到上下文溢出错误，也可能在回合中途压缩。
- 压缩时保留最近的一些消息不变，使用可配置的 token 预算（默认 20k token，约 5–20 个回合）。较旧的消息被提取、序列化并总结。
- 压缩使用独立的提示词，系统提示为“你是上下文总结助手”，用户消息要求生成包含 goal、progress 和 key decisions 的结构化摘要。这类似于值班交接简报，只保留对后续请求仍然重要的上下文。

## 小结

有效压缩对于长时间编码会话至关重要。Pi 通过专门的总结模型，将冗长历史提炼为精炼摘要，从而在有限的上下文窗口内持续工作。
