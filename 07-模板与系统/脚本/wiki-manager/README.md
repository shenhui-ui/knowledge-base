# wiki-manager 教程

> 一份把 `wiki-manager.skill` 拆解给「想用、想改、想排错」的人看的指南。

---

## 它是什么

`wiki-manager`（知识库管家）是基于 Karpathy LLM Wiki 方法论的个人知识库管理系统。它把你扔进收件箱的素材（笔记、文章、链接摘录）按规则沉淀成结构化的 wiki 文章，帮你按问题检索，并在你写完以后替知识库做体检。

整套系统由四件事组成：

| 能力 | 解决什么问题 | 入口脚本 |
|------|--------------|----------|
| **init** | 从零搭出一个 9 分区的 wiki 骨架 | `scripts/init.py` |
| **ingest** | 把收件箱里的素材提炼成主题区里的 wiki 文章 | 见「ingest 工作流」章节 |
| **query** | 拿自然语言问题去命中已有文章，给出摘要与来源 | `scripts/query.py` |
| **lint** | 检查索引一致性、链接有效性、Unicode 顺序等六类问题 | `scripts/lint.py` |

---

## 适用场景

- 想建一个能自我生长的本地 Markdown 知识库（不是云端的 Wiki 站点）
- 已经在 Obsidian、VS Code、Logseq 等工具里写 markdown，想给它们加一套机器可读的"管家规则"
- 想让 LLM 帮你维护知识库而不是每次都重新解释"这堆文件该怎么看"
- 有一批素材（会议纪要、技术文章、读书笔记）想沉淀为可检索的条目

不适合：单纯想要一个云端 Wiki 协作平台（去用飞书知识库/Notion/Confluence）；做高频实时协同编辑的团队 wiki（这套是给单人或小团队本地用的）。

## 5 分钟快速上手

```bash
# 1. 初始化知识库骨架
python3 scripts/init.py --wiki /path/to/your/wiki

# 2. 把素材放到 00-收件箱/，文件名加 @manual 后缀表示手动处理
cp my_note.md /path/to/wiki/00-收件箱/RAG\ 检索增强生成\ @manual.md

# 3. 按 article_template.md 写 wiki 文章到可写区
# （04-AI与机器学习/RAG 检索增强生成.md）

# 4. 同步更新索引（Unicode 字母序插入 [[文章名]]）
# （编辑 07-模板与系统/MOC/索引.md）

# 5. 跑 lint 检查
python3 scripts/lint.py --wiki /path/to/your/wiki

# 6. 检索
python3 scripts/query.py "RAG 是什么" --wiki /path/to/your/wiki
```

跑完这六步，你就拥有了一个能搜、能体检的本地知识库。

## 目录结构与读写分区

初始化后会建出 9 个分区。每个分区的「性质」决定了谁能往里写：

```
your-wiki/
├── 00-收件箱/                # 只读：素材区，AI 不写
├── 01-日记/                  # 自由：每日笔记
├── 02-资讯日报/              # 只读：自动管线写入
├── 03-软件开发/              # 可写：wiki 主题区
├── 04-AI与机器学习/          # 可写：wiki 主题区
├── 05-数据分析/              # 可写：wiki 主题区
├── 06-项目/                  # 可写：项目相关文档
├── 07-模板与系统/
│   ├── MOC/                  # 索引 + 操作日志（可写）
│   ├── .模板/                # 禁入：系统模板
│   ├── .obsidian/            # 禁入：Obsidian 配置
│   └── 脚本/                 # 禁入
└── 99-归档/                  # 已处理素材的归宿
```

| 区域 | 性质 | 谁可以写 |
|------|------|----------|
| 03-软件开发 / 04-AI与机器学习 / 05-数据分析 / 06-项目 | 可写 | AI 在确认后写入 |
| 07-模板与系统/MOC/索引.md | 可写 | 增删条目时同步 |
| 07-模板与系统/MOC/操作日志.md | 可写 | 追加条目 |
| 00-收件箱 / 02-资讯日报 / 07-模板与系统/附件/ | 只读 | AI 只能读 |
| 07-模板与系统/.模板/ / .obsidian/ / 脚本/ | 禁入 | 任何情况下都不读不写 |

为什么这样分？让 AI 永远清楚"我能动什么"。修改已有 wiki 文件前要先告诉用户——除了 init / ingest 端到端验证场景。

## 文件命名与 frontmatter 规范

### 文件名

- 用中文描述性名（不要数字前缀），如 `RAG 检索增强生成.md`、`Pandas 数据处理.md`
- 含空格合法，但所有处理**必须**用 Python/Node/Go 等能正确处理 UTF-8 与空格的工具
- 绝不要用 shell `for x in $(ls ...)` 这类会按 IFS 切分含空格/中文文件名的命令

### wiki 文章 frontmatter

```yaml
---
type: ingest-note         # 必填：固定值
source: <原文 URL 或来源名>  # 必填
date: YYYY-MM-DD          # 必填
tags: [tag1, tag2]        # 推荐
---
```

### wiki 文章正文

- H1 标题与文件名一致
- 开头一句话定义/概述（≤60 字）
- 核心要点、子主题段落每段 ≤150 字
- 末尾 `## See Also` 段用 `[[文章名]]` 形式列双向链接
- 引用源数据用具体数字而非"很多/大量"

### 收件箱素材 frontmatter

```yaml
---
type: source-material
date: YYYY-MM-DD
source: <原文 URL 或来源名>
---
```

文件名加 `@manual` 后缀（如 `RAG @manual.md`）表示这是手动流程要处理的素材；自动管线的素材不加。

## 四大核心命令详解

### 1. init — 一次性建骨架

```bash
python3 scripts/init.py --wiki /path/to/your/wiki
```

做的事：

1. 创建 9 个分区目录
2. 创建 `07-模板与系统/MOC/索引.md`（含 `<!-- index:start/end -->` 标记）
3. 创建 `07-模板与系统/MOC/操作日志.md`（含 `<!-- log:start/end -->` 标记）

幂等：已存在的目录/文件会跳过，缺失的会补齐。可以放心重复跑。

### 2. ingest — 素材沉淀七步

1. 把素材存为 `00-收件箱/<name> @manual.md`（手动流程加 `@manual` 后缀，自动管线由调度器加 `@auto`）
2. 读 `07-模板与系统/MOC/索引.md` 查重
3. 筛选：高价值/新主题 → 沉淀；重复 → 合并；广告/无内容 → 丢弃
4. 按 `article_template.md` 写 wiki 到对应可写区，frontmatter 含 `type: ingest-note` + `source` + `date` + `tags`
5. 索引按 Unicode 字母序插入 `[[文章名]]` 条目
6. 归档素材到 `99-归档/`
7. 追加操作日志到 `07-模板与系统/MOC/操作日志.md`

合并与新建的选择：查重命中已有文章 → 合并（更新 frontmatter、补新章节）；未命中 → 新建文章。

### 3. query — 三层匹配检索

```bash
python3 scripts/query.py "<问题>" --wiki /path/to/your/wiki
# 例：python3 scripts/query.py "Transformer 是什么" --wiki ./wiki
```

匹配策略按优先级回退：

1. **子串优先**：文章名 ⊂ query。比如 query 里有 "RAG 检索增强生成" 这种完整标题，直接命中
2. **关键词匹配标题**：query 中任意词 ⊂ 文章名。比如 "BERT 模型" 命中《BERT》文章
3. **非泛词搜索正文**：去掉泛词（见下）后用剩余关键词在正文里搜

泛词黑名单（这些词太常见，不用来做内容匹配）：

```
模型 / 架构 / 预训练 / 编程 / 生成 / 图像 / 模板 /
部署 / 处理 / 是什么 / 怎么用 / 如何 / 进展 /
区别 / 应用 / 方法 / 特点 / 作用 / 影响
```

返回格式：每条命中给出文章名、所属主题区、source、date，以及正文前 300 字的摘要。

**示例输出：**

```
Query: RAG 是什么
命中: 1 条
============================================================

## RAG 检索增强生成（04-AI与机器学习）
源: 检索增强生成技术综述 | date: 2026-08-12

# RAG 检索增强生成

> 一种把外部知识库检索与大模型生成结合的技术范式，先召回相关文档再让模型基于文档作答。
...
```

### 4. lint — 六项检查 + 自动修复

```bash
python3 scripts/lint.py --wiki /path/to/your/wiki        # 只查
python3 scripts/lint.py --wiki /path/to/your/wiki --fix   # 查 + 自动修
```

六项检查：

| # | 检查 | 含义 |
|---|------|------|
| 1 | 索引 vs 实际文章 | 索引里的 `[[文章名]]` 要在主题区里有对应文件，反之亦然 |
| 2 | 主题区分布 | 列出每个主题区有多少篇文章 |
| 3 | 链接目标存在性 | 所有 `[[X]]` 里的 X 都要是真实存在的文章名 |
| 4 | 双向链接对称性 | A 链接 B 时，B 也应该链接回 A；不强制对称，但会报告"意向性单向" |
| 5 | 索引 Unicode 顺序 | 索引按 Unicode 码点字母序排列 |
| 6 | 收件箱/归档状态 | 收件箱应空（处理过的素材已归档） |

`--fix` 模式会自动修两类问题：

- 索引里漏了某篇文章 → 补上对应条目
- 索引里指向了不存在的文件 → 移除该条目

不能自动修的（矛盾、孤立页）会以警告形式报告，由你判断。

**示例输出：**

```
============================================================
知识库 lint — /path/to/your/wiki
============================================================

【1. 索引一致性】
   索引: 7 条 | 文章: 7 篇
   ✅ 匹配: 7/7

【2. 主题区分布】
   03-软件开发: 2 篇
   04-AI与机器学习: 3 篇
   05-数据分析: 1 篇
   06-项目: 1 篇
   总计: 7 篇

【3. 链接目标存在性】
   ✅ 全部有效

【4. 双向链接对称性】
   ⚠️  单向链接: 知识库搭建项目 → RAG（反向缺失）
   ⚠️ 1 条意向性单向

【5. 索引 Unicode 顺序】
   ✅ 顺序正确（7 条）

【6. 收件箱/归档】
   收件箱: 0 个 ✅ 空
   归档: 7 份

============================================================
错误: 0 | 警告: 1
✅ 全部通过
============================================================
```

## 检索原理（为什么不只是 `grep`）

朴素 `grep` 全文匹配会引入两类噪音：

1. **泛词污染**："模型"、"预训练" 等词在几乎每篇 AI 文章里都出现，导致命中过多
2. **上下文缺失**：`grep` 不知道你问的是文章名还是正文

三层匹配的设计动机：

- **子串优先**是为了让"我提了完整标题"这种最高意图不被淹没
- **关键词匹配标题**是为了让"我问了一半"也能命中（"BERT" 命中《BERT》而不是《Transformer》）
- **非泛词搜索正文**才是兜底，且在兜底之前要把 19 个泛词剥掉

实测下来，对 6–7 篇文章的小型知识库，召回率与精确率都接近 100%；超过 50 篇要考虑加 BM25 等更复杂的排序。

---

## lint 原理（为什么是这六项）

| 检查 | 触发的"反例" |
|------|--------------|
| 索引一致性 | 写完文章忘了改索引 / 删了文章忘了清索引 |
| 主题区分布 | 文件乱放（如把项目文档放进 04-AI） |
| 链接目标存在性 | 改文件名后忘了改文中 `[[X]]` |
| 双向链接 | 知识库长了以后，孤岛页不知道自己还连着谁 |
| Unicode 顺序 | 中文（U+77E5）排在 ASCII 大写字母之后、新中文之前要按 codepoint，不能用拼音 |
| 收件箱/归档 | 素材处理完应该及时归档，否则下次还会被重新处理 |

最容易被忽视的是 **Unicode 顺序**：中文文件的码点远比 ASCII 大，混排时按"英文大写 → 中文"的顺序插入索引才是对的，按拼音排就错了。

## 已知坑与对策

### 坑 1：shell 切分含空格文件名

**症状**：`Pandas 数据处理.md` 在 `for x in $(ls *.md)` 里被切成 "Pandas" 和 "数据处理" 两个 token，文件名全乱了。

**对策**：永远用 Python（`pathlib`）或 Node 处理文件遍历，不要在 shell 里 for-loop 跑文件名。`scripts/lint.py` 和 `scripts/query.py` 都用 `pathlib.Path.glob` 正是为此。

### 坑 2：泛词误报

**症状**：query 是 "GPT 模型"，结果命中所有提到 "模型" 的文章。

**对策**：见"检索原理"章节——泛词黑名单 + 标题优先。如果新词被频繁误报，加进 `scripts/query.py` 的 `GENERIC` 集合。

### 坑 3：中文名 Unicode 顺序

**症状**：索引里 `Transformer` 排在 `知识库搭建项目` 之前，看起来合理；实际按 codepoint `Transformer` (T=0x54) 确实在 `知` (U+77E5) 之前。但如果按拼音排，"Transformer" 在 "Z" 开头就要排到 "知识库" 之后。

**对策**：始终用 `sorted(entries, key=lambda x: x.encode('utf-8'))` 这种 codepoint 排序，**不要**用拼音库。

### 坑 4：索引条目假阳性

**症状**：`MOC/索引.md` 里为了演示会写一句"格式：`- [[文章名]]`"，正则抓取时把 "文章名" 也当成有效条目。

**对策**：`scripts/lint.py` 的 `scan_wiki` 里加了过滤 `if e != '文章名'`，且 `<!-- index:start -->` 到 `<!-- index:end -->` 之间的内容才是真条目。

### 坑 5：双向链接假阳性

**症状**：A 文章里 "提到" B 但不是真正的链接（不应回链），被 lint 报为"单向链接警告"。

**对策**：双向链接**只是警告不报错**。有些"意向性单向"是合理的（如"项目主页"指向"概念解释"页面但概念页没必要回链到项目），保留警告由人判断。`--fix` 不会动这一类。

## 进阶用法

### 改泛词黑名单

编辑 `scripts/query.py` 顶部的 `GENERIC` 集合：

```python
GENERIC = {
    '模型', '架构', '预训练', '编程', '生成', '图像', '模板',
    '部署', '处理', '是什么', '怎么用', '如何', '进展',
    '区别', '应用', '方法', '特点', '作用', '影响',
    # 加你这边的高频泛词，比如 '优化' / '框架' / '实践'
}
```

### 自定义主题区

`scripts/lint.py` 和 `scripts/query.py` 顶部的 `TOPICS` 列表：

```python
TOPICS = ['03-软件开发', '04-AI与机器学习', '05-数据分析', '06-项目']
```

增删后两处都要同步改。同时要相应调整 `scripts/init.py` 里的 `DIRECTORIES` 列表。

### 在 CI/定时任务里跑 lint

```bash
# 每天跑一次，错误时非零退出码
python3 scripts/lint.py --wiki /path/to/wiki || \
  python3 scripts/lint.py --wiki /path/to/wiki --fix
```

适合放进 `aily-cli auto` 的 cron 触发（每天 9 点跑一次，作为知识库的"晨检"）。

### 把索引导出为目录页

`07-模板与系统/MOC/索引.md` 本身就是 wiki 入口，可以被任何 Markdown 渲染器（Obsidian / VS Code 预览）直接看到。进阶玩法：用 `moc` 类工具自动从索引生成反向链接图谱。

## 故障排查

### Q：跑 `lint.py` 报 `ModuleNotFoundError`

A：脚本只用 Python 标准库，不需要 pip install。检查 Python 版本 ≥3.6。

### Q：`query.py` 找不到文章，但文章确实在主题区里

A：八成是索引没同步——跑 `lint.py --fix` 重建索引，或手动在 `MOC/索引.md` 里加 `[[文章名]]`。

### Q：把所有文章都报成"索引失效"

A：检查文件名是否含特殊字符。中文 + 空格合法，但 `.` `/` 等不行。也要确认 frontmatter 是否被破坏（缺失 `type: ingest-note` 不影响 lint，但缺失 `[[文章名]]` 在正文中会让链接检查不通过）。

### Q：双向链接警告太多

A：先看警告是否合理——确实需要双向的就补上；意向性单向的（如总览页指向各分页）忽略即可。改 `lint.py` 的 `check_bidirectional` 改为只报错不警告是另一个选项，但默认行为更安全。

### Q：Unicode 顺序检查报"位置 N 错乱"

A：基本是手动改过索引没排序。复制当前所有 `[[X]]` 条目，跑 `python3 -c "print('\n'.join(sorted(open('idx.txt').read().splitlines(), key=lambda x: x.encode('utf-8'))))"` 拿到正确顺序贴回去。

### Q：自动修复后内容丢了

A：lint --fix 只动 `MOC/索引.md` 的 `<!-- index:start -->` 到 `<!-- index:end -->` 之间那部分，其他内容不动。如果丢了，多半是手动改坏了——读 `操作日志.md` 看最近一次 ingest 记录回滚。

## 与 Karpathy LLM Wiki 方法论的关系

Karpathy 提的 LLM Wiki 核心三原则：

1. **自生长** — 内容由 LLM 与素材驱动持续追加，不是人手维护
2. **可检索** — 任何问题都能找到对应页面，且页面之间双向链接形成图谱
3. **可体检** — 结构化规则能机器化校验，不依赖人记得规则

`wiki-manager` 是这套方法论的最小可执行实现：

- 收件箱 → ingest 解决"自生长"
- 三层匹配 query 解决"可检索"
- 六项 lint + --fix 解决"可体检"
